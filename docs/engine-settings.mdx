Open a device's Ollama, LM Studio, llama.cpp, or vLLM row and expand **Settings**.
Edit the server port, proxy port, and engine arguments, then select the green **Apply** button.
A paired device that supports settings can be edited from another device in the
cluster.

PAIR fixes the executable, lifecycle commands, and loopback address. Unsupported
vendor options can fail at startup.

For installing, starting, and uninstalling engines, refer to
[Managing engines](engine-lifecycle.mdx).

## Model Download Source

For llama.cpp, choose **Hugging Face** (the default) or **ModelScope** in
**Model download source**, then select **Apply**. A running engine asks to restart
before changing sources; a stopped engine stays stopped. The choice is saved
on the device running the engine and also selects the source used by the model
browser and search. Public GGUF repositories use the same `owner/repository:quant`
names, with `Q4_K_M` offered in the browser. Repository availability can differ
between sources. Downloaded files stay in llama.cpp's existing cache.

PAIR sets llama.cpp's `MODEL_ENDPOINT` only for ModelScope. Hugging Face keeps
existing endpoint settings, including custom mirrors. ModelScope downloads do
not forward Hugging Face credentials; private or gated ModelScope models are
not supported. An engine adopted from another application keeps its original
download endpoint; PAIR cannot change the environment of an already-running
process. This setting stays read-only until that engine is stopped in its own
application and takes effect when PAIR launches it. A paired device must report
support for source selection before the dropdown is editable; other settings
can still be changed on devices that support settings editing.

ModelScope downloads verify the complete file's size and SHA-256 before reporting
success. Interrupted downloads restart from the beginning so cached partial
data cannot bypass verification.

## Argument Notation

The text contains engine arguments and optional leading environment assignments.
PAIR supplies the executable and startup subcommand. Leave the text empty to use
managed defaults. Tokens are passed directly to the engine, using the same
notation on every operating system.

- Spaces, tabs, and line breaks separate unquoted tokens.
- Single quotes enclose literal text. Double quotes enclose literal text with
  two escapes, `\"` and `\\`. Any other backslash stays literal, so a Windows
  path such as `C:\new\tools` needs no doubling.
- A quoted and an unquoted part can form one token, as in `--name="two words"`.
  An empty quoted string is an empty argument.
- Nothing is expanded: `$HOME`, `%USERPROFILE%`, `{port}`, and `~` are literal,
  and there are no comments, pipelines, redirects, or command substitution.
  Unquoted `|`, `&`, `;`, `<`, `>`, a backtick, or `$(` is rejected. Quote them
  when the engine needs that character.
- At most 16 KiB and 256 tokens, valid UTF-8.

Environment assignments go first, followed by engine arguments:

```text
OLLAMA_ORIGINS="https://example.com"
--port 1235 --bind 127.0.0.1
```

## Environment Variables

Environment assignments are saved and passed literally to the engine on every
launch. PAIR does not maintain a list of supported variables or validate their
engine-specific values. Editing or removing one takes effect at the next launch.

Managed CORS settings, including LM Studio's `--cors` switch, can only be changed
on the device running the engine. A paired device can preserve an existing CORS
policy while changing other settings, but cannot enable, disable, or replace it.
Other environment assignments can also be edited from a paired device.

Origin lists need a scheme and a specific host, so bare `localhost` and `*` are
rejected, including wildcards hidden inside extra quotes. Wildcard subdomains
such as `https://*.example.com` and ports such as `http://localhost:*` are supported.
Managed llama.cpp starts with an empty origin list, so cross-origin browser
access is disabled until specific origins are added locally. List only the
origins you want to allow. This is how you give a web page access to your models.
PAIR's local endpoints add no permissive default of their own, so a browser
reaches a model through PAIR only where the engine would have allowed it directly.
For a request that spans the cluster, every engine that answers has to allow the
origin.

An engine does not need a CORS launch option to work with PAIR. The proxy follows
the engine's HTTP responses regardless of how its CORS policy is configured.
If the engine grants no CORS permission, PAIR does not add permission for it.

Startup failures include a bounded excerpt of the engine's own output. PAIR
redacts supplied values by exact match, but an engine can transform or encode
them. Do not put secrets in launch values.

## Ports and Validation

PAIR understands only the networking controls needed to keep engine and proxy
configuration consistent:

| Engine | Server Port | Loopback Bind | Browser Access |
| --- | --- | --- | --- |
| Ollama | `OLLAMA_HOST=127.0.0.1:<port>` | The host in `OLLAMA_HOST` | `OLLAMA_ORIGINS` |
| LM Studio | `--port`, `-p` | `--bind`, `LMS_SERVER_HOST` | `--cors` |
| llama.cpp | `--port` | `--host` | `--cors-origins` |
| vLLM | `--port` | `--host` | Not managed |

For LM Studio, `--port 1235`, `--port=1235`, `-p 1235`, `-p1235`, and `-p=1235`
all synchronize the same server-port field. Conflicting repetitions and invalid
ports are rejected. Write managed short options separately. Bundles containing
them are ambiguous and rejected. CORS switches do not take `=true` or `=false`.
Add or remove the switch locally. Origin lists are normalized before validation,
and conflicting repeated lists are rejected. Other vendor options remain opaque.
llama.cpp must remain in router mode. Model-selection arguments such as `-m`
or `-hf` switch it to an incompatible single-model server and fail readiness.
vLLM always serves one model: its launch arguments name that model with
`--model <Hugging Face id>`, and changing it restarts the engine. At every start
PAIR sizes the rest for that model: a 64K context (`--max-model-len`, shrunk if
the free GPU memory cannot hold it), YaRN rope scaling when the model's own window
is smaller (for example Qwen3-8B's 40,960 tokens), a GPU memory share just large
enough for the weights and that context, so other engines can run alongside it,
and a limit of 32 requests at a time (`--max-num-seqs`).
Memory sizing is left to the engine when CUDA device visibility is configured,
more than one physical GPU is reported, or the launch explicitly sets `--dtype`
or `--kv-cache-dtype`. This avoids sizing a different device or storage format
from the one the engine uses. A model that is not
downloaded yet, such as the default on a fresh install, has its configuration
and chat template fetched first and is then set up the same way, tool calling
included, before vLLM downloads its weights. Hugging Face settings in vLLM's
launch settings apply to PAIR's own requests, downloads and deletes too:
`HF_HUB_OFFLINE` or `TRANSFORMERS_OFFLINE`, `HF_TOKEN` (not sent when
`HF_HUB_DISABLE_IMPLICIT_TOKEN` is set), a mirror in `HF_ENDPOINT`, and a cache folder in
`HF_HUB_CACHE` or `HF_HOME`, or `--download-dir` in the launch text, which the model list
then shows. Arguments you add to the launch text,
such as your own `--max-model-len`, `--gpu-memory-utilization` or
`--max-num-seqs`, take precedence, and a launch with
`--tensor-parallel-size` or `--pipeline-parallel-size` is left as written. PAIR
also turns on tool calling, which agent clients require: it checks how the
model's chat template writes a tool call and picks the vLLM parser that reads
that format (for example `hermes` for Qwen3, `qwen3_coder` for Qwen3.5 and
Granite 4.2). For a model no vLLM parser can read, such as Nemotron Nano v2,
tool calling stays off and vLLM answers a request that asks for tool calls with an
error. To choose a parser yourself, add `--tool-call-parser <name>` to the
launch text.

Changing the server-port field updates the port in the command. Editing the
command's port updates the numeric field. If both are edited before validation
finishes, the numeric field takes precedence. The server and proxy must use
different ports. A collision opens an error dialog explaining which port
collides. Invalid settings and failed saves also open an error dialog.

**Apply** validates the complete change. PAIR asks for confirmation only when a
running engine needs to restart. Progress appears as a spinner inside **Apply**.
A running engine restarts for launch and server changes. Changing only the proxy
port leaves the engine running. Stopped engines remain stopped. Saved settings
survive restart.

## Concurrent Edits

Changes from another device update a clean editor. An unfinished draft stays
intact, and applying a stale draft opens an error dialog. **Reload saved
settings** deliberately discards that draft. Failed starts retain the saved
settings for correction and show one error dialog. Validation on leaving a field
quietly synchronizes ports. Errors appear only when you select **Apply**, without
duplicate text below the command.

Offline, unpaired, or older devices cannot be edited. A process started outside
PAIR can require stopping it in its own application before changing its launch.
The displayed arguments describe a future PAIR launch, not an external process's
original arguments.
